# 小猿口算「比大小」外挂制作方案（攻击面分析）

> 📍 注：文中 `decompiled/...` 路径为坐标参考，该目录不入仓库（以 zip 分发）；原本地绝对路径链接已转为纯文本坐标。

> 前提：判题是**本地**完成的。题目答案（`rightAnswers`）随题目一起下发到客户端，业务层只做「识别字符串」与「rightAnswers」的精确相等比对（`Intrinsics.areEqual`），无服务端二次判题、无笔画几何校验。因此外挂的核心目标不是"骗过服务端判题"，而是**在本地拿到答案 / 让本地比对恒真**。

***

## 1. 攻击面结论

| 防护点                      | 强度       | 对外挂的阻碍  | 绕过方式        |
| ------------------------ | -------- | ------- | ----------- |
| 加壳                       | 无        | 无       | 无需处理        |
| Java 反调试/Xposed/Frida 检测 | 无        | 无       | 无需处理        |
| Java 签名/完整性校验            | 无        | 无       | 重打包重签名即可跑   |
| root 检测                  | 弱（仅崩溃日志） | 无       | 无需处理        |
| 模拟器检测                    | 无        | 无       | 可跑模拟器       |
| 请求签名 native              | 中        | 伪造请求需复刻 | 响应侧 hook 可绕 |
| 时间对齐/防重放                 | 中        | 设备时间需准  | 保持系统时间准确即可  |
| 设备指纹/风控（数盟）              | 中        | 上报默认关闭  | hook 上报点    |

**总体难度：低。** 因判定本地化 + 无加固 + 无应用级签名校验，最小可行外挂只需一个 Frida 脚本或 Xposed 模块，无需触碰 native 签名。

***

## 2. 三条实现路线（按复杂度递增）

### 路线 A：Frida 动态插桩（推荐，免重打包）

* 优点：不改 APK、不重签名、规避签名校验问题（即便未来加了校验也不受影响）。

* 核心 hook 点（源码定位）：

| Hook 目标 | 位置                                                                      | 作用          |
| ------- | ----------------------------------------------------------------------- | ----------- |
| 答案字段读取  | 题目 DTO 的 `rightAnswers` getter                                          | 直接读出本题正确答案  |
| 识别结果比对  | `kotlin.jvm.internal.Intrinsics.areEqual`（内联后为 `Objects.equals`）或业务层比对点 | 强制恒真        |
| 识别器入口   | `br.d`（识别器识别方法）                                                         | 返回伪造的"正确符号" |
| 提交接口    | `StudyExerciseResultApiService.submitExercise`                          | 拦截/伪造提交（可选） |

* 伪代码：

```javascript
// Frida JS
Java.perform(function () {
  // 1) 读答案：hook 题目响应解析，打印 rightAnswers
  // 2) 强制判对：hook Intrinsics.areEqual 返回 true
  var Intr = Java.use("kotlin.jvm.internal.Intrinsics");
  Intr.areEqual.overload('java.lang.Object','java.lang.Object').implementation = function(a,b){
    return true;
  };
});
```

### 路线 B：Xposed / LSPosed 模块（持久化，需 root）

* 在 `attachBaseContext` 后即可 hook（无加固，无需等壳解压）。

* hook 点与路线 A 相同，用 Xposed `XposedHelpers.findAndHookMethod`。

* 优点：安装一次常驻；缺点：需 root + 框架，且会被数盟/MA 指纹标记为高风险设备（但上报默认关闭）。

### 路线 C：重打包静态篡改（无需 root，但需重签名）

* 因**无应用级签名校验**，重签名后能正常运行。

* 篡改点：把比对逻辑改恒真，或把 `rightAnswers` 直接展示到 UI。

* 需处理：`libmsaoaidsec.so`（OAID）可能因证书/包名变化失效——但 OAID 失败不影响判题，仅影响设备 ID。

* 缺点：需每次版本更新重做；若未来加签名校验则失效。

## 3. 需要攻克的三个关键点（进阶 / 主动提交成绩场景）

若外挂只需"读答案 + 本地判对"，**无需**处理以下三项；仅当需要**主动向服务器提交伪造成绩**或**自动化脚本直接调接口**时才需要：

### 3.1 请求签名（`libRequestEncoder.so`）

* 入口：`e.zcvsd1wr2t(str, "wdi4n2t8edr", (int)(x.k().s()/1000))`

* 密钥：`"wdi4n2t8edr"`（p005ds/c5.java:L52）

* 绕过策略（二选一）：

  1. **JNI 直调**（最简单）：在 Frida/Xposed 中直接调用该 native 方法为任意字符串生成 sign，无需逆向算法。
  2. **复刻算法**（离线）：用 IDA/Ghidra 反汇编 `libRequestEncoder.so` 导出/符号 `zcvsd1wr2t`，恢复具体算法（疑似 MD5/HMAC，需自行验证）。

### 3.2 时间对齐 / 防重放

* `tg/x` 存储 `time.delta`，由 `cq/l` 从 HTTP `Date` 头解析写入；签名时间戳用 `x.k().s()`。

* 绕过：保持设备系统时间与服务器一致即可（签名时间戳 = 校正后时间）。

* 若时间异常，会触发 `/debug/leo/abnormalTimeDelta` 风控埋点。

### 3.3 设备指纹 / 风控上报

* 链路：`shepherd/a` → `shepherd/b` → 数盟 `cn/shuzilm/core/Main`（`libdu.so`）→ `syncDu(did,sessionId,lid)`。

* 关键事实：`shumengReportEnable` 默认 `p()==false`（**上报默认关闭**）。

* 绕过：若某版本默认开启，hook `shepherd/a.shumengReportEnable` 返回 false，或 hook `wl.e.a().log` / `wl.l.j` 屏蔽上报。

## 5. 风险与边界说明

1. 本方案仅用于**安全研究 / 攻防对抗评估**，对应"反外挂检测机制排查"的研究目标；实际制作外挂用于考试/作业作弊存在合规与伦理风险，请自行评估使用场景。
2. 数盟 `libdu.so` 可能存在环境采集（本报告 strings 扫描未发现明显 root/模拟器检测命中，但 SDK 通常采集设备属性用于风控），长期高频异常行为可能触发服务端风控封号。
3. 上述 hook 点基于当前版本静态反编译结果，跨版本可能因混淆改名（`p005ds/c5`、`cq/o`、`br/d` 等）而失效，需按行为特征重新定位。
